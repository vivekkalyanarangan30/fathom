How Fathom Works

How top-k attention finds its k keys, what Loki, Double Sparsity, SparQ, landmark selection and thumbnail scans each read to do it, and the one change we make: read each channel to the depth its evidence deserves, straight out of the K cache. One worked example runs through every method.

Step 1

The job every method shares

At each decode step the model has one new query vector q per head and n stored keys. Dense attention scores all n keys and reads all of their values. Top-k attention keeps only the k best-scoring keys (plus a few sink and local tokens), so the value read shrinks from n rows to k. That leaves a circularity: to know which k keys win, you still have to score all n.

Every method in this page resolves the circularity the same way. It keeps a cheap summary of each key, scans all n summaries to rank the keys, then fetches the full keys and values of the winners. The summary scan is a stream of n small records, so its cost is bits per token, and at long context that stream is the largest thing the step reads.

step cost ≈ weights + n × (summary bits / 8) + k × (full K+V row bytes)

Numbers for Qwen3-8B (36 layers, 8 KV heads of 128 channels) at 32k tokens. Dense attention reads the whole KV cache, 4.8 GB per step. Top-k with k=512 per query head fetches the union of the four heads' winners, about 200 MB of rows per step, a cost that does not grow with the context, plus the scan. A Loki, Double Sparsity or SparQ (r=32) scan reads 32 coordinates of each key at 4 bits plus an fp16 block scale, 136 bits per token for each of the 288 layer-head pairs: 32,768 × 136 / 8 = 557 KB per pair, times 288 pairs, 160 MB per step at 32k. That term grows with n, reaching 5.1 GB at one million tokens while the winner rows stay near 200 MB. Every bit count on this page is per token, per KV head, per layer, and includes the fp16 block scale of every channel read (16 bits per 64 tokens per channel). Methods differ only in what the summary is, who decides its contents, and when.

The first method to let the query choose. Under grouped-query attention SparQ sums |q| over the heads of the group before picking, so one channel set is read per KV head. On the toy (r=2): the summed |q| is (4, 3, 3, 0.3); channels 0 and 1 are picked (channel 1 wins the tie with channel 2 by index). Where it breaks: two things. It ranks channels by |q| and ignores how much the keys vary in that channel. And it is all-or-nothing per channel: a chosen channel is read at full 4-bit depth, an unchosen one not at all. A variant that lets every head pick its own channels and reads the union is stronger but costs about twice the bytes; the paper reports it once as an ablation.

Step 4

What we do differently, in four moves

Move 1. Rank channels by evidence, not by |q|

A channel's contribution to the score is qj · kj. How much it can separate two keys depends on how much kj varies across tokens as well as on qj. We measure the variance of each channel once, on calibration text, and weight the query with it. Under grouped-query attention the heads that share this KV head are summed, so one plan serves the group and the read is never a union.

gj = Σheads in group qj² · Var(kj)

On the toy: g = [12.22, 3.77, 0.63, 0.00]. Channel 2 scores 0.63 despite head B's weight of -1.0, and channel 3 scores zero although both heads have a nonzero weight there. SparQ's |q| ranking for head B was [ch1, ch0, ch2, ch3]; evidence ranking is [ch0, ch1, ch2, ch3] for the whole group.

Move 2. Choose a depth per channel, not membership

Every method so far reads a channel at full precision or not at all. Quantization error shrinks by 4× for every extra bit, so the value of one more bit on a channel is proportional to gj · 4-t where t is the depth it already has. The first bit on a strong channel is worth far more than the fourth; the fourth bit on a strong channel can be worth less than the first bit on a weak one. Handing out bits in order of marginal value is reverse water-filling, and it has a closed form: every channel gets depth

tj = clip( round( log4( gj / θ ) ), 0, 4 )

where θ is the single water line, found by bisection so that Σ tj hits this layer's bit budget. Channels below the line read nothing.

At 8 bits per token, the same budget Loki, Double Sparsity and the thumbnail had, ours is the only one that gets head B right, because a single bit of channel 2 is enough to separate t0 from t3, and the budget could afford it once channel 3 was dropped.

ours at 8 bits: a staircase, depths 4 · 3 · 1 · 0

Compare the shapes in Step 3: the competitors read whole columns (channel picks) or whole rows (uniform depth). We read a staircase. On real 128-channel keys the staircase at mean 48 bits typically reads about 30 channels at 1 to 4 planes each.

Move 3. Store the K cache so a staircase is a contiguous read

Reading "the first t bits of channel j for all tokens" is only cheap if those bits sit next to each other in memory. So the 4-bit K cache is stored channel-major in bit planes: for each block of 64 tokens and each channel, the 64 most-significant bits form one 8-byte word, the next bits the next word, and so on. Codes are offset-binary mid-rise, so the first t planes of the 4-bit code are exactly the t-bit quantizer with the same scale; no second copy at lower precision is needed.

Two consequences. There is no separate index: the scan reads a prefix of the K cache itself, so the 16.5 bytes per token of Double Sparsity's label cache and the 32 bytes per token of a landmark index do not exist. And a prefix read is a contiguous run, which is what makes the bytes turn into time on PCIe (Step 6).

Move 4. Budgets per layer, and the basis rule

Layers differ: early layers need 96 to 128 bits to keep their error down, late layers are fine at 24 to 32. A greedy allocation on calibration text hands out a fixed mean (48 or 64) across layers. It roughly halves the error on the QK-norm models (Qwen3) and is neutral or slightly worse on the Qwen2.5 models, and a plan calibrated at one context length does not transfer to another, so the flat budget is the default and the plan is a tuning step.

The channel-wise plan assumes score variance is concentrated in raw channels. That holds for QK-normed models (Qwen3). For models without QK-norm (Llama-3.1, Qwen2.5) the variance is spread out, and rotating the keys into their principal basis first, then storing those coordinates in bit planes, restores the concentration. Same water-filling, same layout, one extra offline rotation. Unlike Loki, nothing is truncated: all 128 rotated coordinates are stored, and the query decides how deep to read each.

When bytes become time

Fewer bytes are only faster when bytes are what the hardware is waiting for. Three measured regimes:

regimewhat bindsmeasured
KV and index in GPU memoryarithmetic per scanned bit (on the A100 the planes kernel reaches 75–106 GB/s of HBM bandwidth, the 4-bit channel scans 148–245)the scan kernel itself is 1.4× slower than the 32-channel scan while reading 40% fewer bytes; the scan is 16–24% of sparse attention, so the step lands within a few percent

KV rows and index in host memory (long contexts, many sessions)PCIe bytesGPU time per step at 1M (A100): Fathom 40 and 48 versus SparQ r16, the 32-channel scan, landmarks and the thumbnail as in the paper; at 56 bits Fathom is 1.67× faster than the 136-bit scans and ties SparQ r16 at 1.1–5.3× lower error; at 47 bits it reads 31% fewer bytes than SparQ r16 and SparQ takes 1.11× its GPU time

One more thing the offload runs taught: access pattern matters as much as bytes. Copying each active channel's planes as one contiguous run into GPU memory moves 25–26 GB/s at every run size from 4 KB to 512 KB, the same as a plain memcpy of the same bytes; issuing one copy call per run manages 0.4 GB/s at 4 KB runs (23 µs of issue cost per call). The bit-plane layout makes the contiguous run possible; the landmark index gets it for free but moves four times the bytes.

Step 7

Where it does not help

If the KV cache and the scan index both live in GPU memory, this method is not faster. The scan is 16 to 24% of sparse attention there, and unpacking bit planes costs more arithmetic per bit than unpacking nibbles. Reading half the bytes buys nothing when arithmetic, not bandwidth, is the bottleneck.
No per-token scan separates from another on downstream tasks at k ≥ 64; the differences live in the attention-error proxy and in bytes. The methods that do lose downstream are the block-granular ones.
Timing beyond 128k used synthetic KV contents (calibration keys tiled, random values) because no model here prefills a million tokens. The plans, transfers and kernels are real; the attention outputs are not meaningful.
Step 8

One paragraph, if you keep one thing

Everyone scans a summary of every key to pick the top k. Loki and Double Sparsity pick which coordinates to keep once, offline. SparQ lets the query pick which channels, all-or-nothing, per head. Landmarks pick which blocks. Thumbnails read every channel to the same shallow depth. We let the query decide how many bits of each channel to read, weighted by that channel's evidence for the whole head group, and we store the 4-bit K cache in bit planes so that reading the first t bits of a channel is one contiguous read of the cache itself, with no second index. Same top-k as the exact oracle at 64 to 80 bits per token; 1.4 to 2.6× faster decode when the cache lives in host memory; nothing gained when it does not.
Numbers on this page are from the project's own runs on one A100-SXM4-80GB pod (fidelity, RULER-style tasks, all timing, kernel and PCIe benches), plus Llama-3.1-8B activations captured on an L4 and evaluated with the same code. The tables are generated from the result files by the same script as the paper's. The toy in Steps 2 to 5 is computed with the same quantizer and water-filling code as the experiments. Landmark selection is our simplified reimplementation of the Quest / ShadowKV idea, not their code.
